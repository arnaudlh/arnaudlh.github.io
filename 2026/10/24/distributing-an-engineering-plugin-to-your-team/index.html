Distributing your engineering plugin to the team

Posted on November 19, 2026 by Arnaud

In article 1, we built a small engineering toolkit. In article 2, we tested its skills. Now we need a repeatable way for teammates to install the package and adopt updates.

We will use Git-Ape's public catalog as a concrete distribution example: register a marketplace, install a plugin, and declare repository defaults. The same pattern works for the toolkit from the earlier articles.

VS Code, the Copilot app, and CLI support plugin marketplaces, with different installation and update interfaces. We will use CLI commands for the worked examples and call out those differences.

Engineering plugins series: 1. Build a plugin | 2. Evaluate its skills | 3. Distribute to the team | 4. Manage across the enterprise

Verified November 17, 2026, on macOS with CLI 1.0.104: Git-Ape marketplace registration, browsing, installation, skill discovery, update checks, disabling, enabling, and removal. A synthetic local plugin covered live-directory behavior. Repository-default activation, upgrades between releases, model-driven use, private-repository access, and the other clients' flows were reviewed against documentation only.

Before you start​

Use an account with Copilot access and install the client your team will use. For the CLI examples, have Git available and install and authenticate Copilot CLI. Check copilot --version and copilot plugin --help before following the commands.

Git-Ape's workflows have their own tool and authentication prerequisites. Installing the package does not configure Azure access or its external tools. Try it in a disposable project without production credentials, and keep normal tool approvals enabled.

Start with the audience​

Before choosing a distribution mechanism, decide what "everyone" means:

AudienceDistribution approach
Engineers who want to try the pluginShare the marketplace and installation commands.
Everyone working in a particular repositoryAdd repository defaults, then verify the behavior in the intended client and harness.
Users across many repositoriesInclude installation in developer onboarding or configure user-level settings.
Users on an enterprise's Copilot planDefine enterprise-managed plugin standards, with device management where needed.

Choose the narrowest scope that reaches your intended users. We will start with individual installation, then repository configuration. For voluntary adoption across repositories, add the installation commands to developer onboarding and run them in each engineer's environment.

Git-Ape's README labels the project experimental and not production-ready. Use it as a sandbox example for this walkthrough.

Package versus catalog​

The plugin and the marketplace have different responsibilities:

FilePurpose
plugin.jsonDescribes the plugin and, in Git-Ape's legacy format, locates its component directories.
.github/plugin/marketplace.jsonDescribes a catalog and tells users where to find its plugins.
.github/copilot/settings.jsonDeclares marketplace and plugin defaults for a consuming repository on supported surfaces.

A marketplace can be a Git repository containing a JSON catalog. The plugin may live in that repository or be referenced from another supported source. The shared marketplace reference describes the catalog fields and plugin identities.

Git-Ape keeps its plugin at the repository root and its marketplace catalog under .github/plugin/:

git-ape/
├── plugin.json
└── .github/
    ├── plugin/
    │   └── marketplace.json
    ├── agents/
    ├── skills/
    └── evals/

Here is a shortened version of its catalog, showing only the Git-Ape entry:

{
  "name": "git-ape",
  "owner": {
    "name": "Microsoft",
    "url": "https://github.com/Azure/git-ape"
  },
  "metadata": {
    "description": "Git-Ape Azure deployment agents and skills"
  },
  "plugins": [
    {
      "name": "git-ape",
      "description": "Azure deployment workflows for GitHub Copilot",
      "source": "."
    }
  ]
}

The "source": "." points to the repository root, where Copilot finds plugin.json. Paths are relative to the marketplace root, not the directory containing marketplace.json. If you host several plugins in one repository, entries can point to directories such as "./plugins/platform-review". See GitHub's marketplace creation guide.

Keep version metadata aligned when releasing a plugin. The complete Git-Ape catalog includes version information and another plugin entry; this shortened example omits them. Git-Ape uses the legacy manifest layout. Keep the Agent Plugins schema and fixed component locations from article 1 when packaging your own toolkit; adding a catalog does not require changing its format.

Give users a short installation path​

Before installing, review the publisher, bundled scripts, hooks, and external connections. Do this for packages from a marketplace as well as direct installations.

For Copilot CLI, Git-Ape's installation guide documents this flow. The browse step lets users inspect the catalog before installing:

copilot plugin marketplace add Azure/git-ape
copilot plugin marketplace browse git-ape
copilot plugin install git-ape@git-ape
copilot plugin list

There are two names in git-ape@git-ape: the plugin name comes before @, and the registered marketplace name comes after it. The repository name used when adding the marketplace is a source; the marketplace's own name becomes its registration key. See GitHub's installation guide for the complete command flow.

Start a new CLI session and inspect the available components:

/skills list
/agent

Checking the inventory is only the first step. Try a low-risk prompt:

Use the prereq-check skill to report which required tools are missing.
Do not install tools, change configuration, sign in, or deploy anything.

Inspect the proposed actions and the skill-loading evidence. Confirm that the response reports prerequisites without making changes. Use this same read-only check after installation in each client.

Distribute from a private internal Git URL​

The catalog and plugin can stay in a private repository. Use your Git host's clone URL, rather than a browser page, raw JSON link, or intranet download link. Copilot CLI supports Git URLs for marketplace registration and direct plugin installation; see the CLI plugin reference.

For example, the fictional company OctoCorp uses GitHub Enterprise Cloud on GitHub.com and hosts a private repository at https://github.com/octocorp/engineering-plugins. The repository contains .github/plugin/marketplace.json with the marketplace name octocorp-engineering, and a plugin named engineering-toolkit at its root. Replace the sample organization and repository with your own.

git ls-remote https://github.com/octocorp/engineering-plugins.git HEAD
copilot plugin marketplace add https://github.com/octocorp/engineering-plugins.git
copilot plugin marketplace list
copilot plugin marketplace browse octocorp-engineering
copilot plugin install engineering-toolkit@octocorp-engineering
copilot plugin list

git ls-remote is a read-only access check. Run it in the same environment as Copilot, after connecting to the required VPN or corporate network and configuring your host's supported Git authentication. For HTTPS, use an approved credential manager; for SSH, use the host's SSH clone URL with an authorized key and verified host identity. Follow your organization's SSO and certificate requirements. Do not put tokens in URLs, catalog files, repository settings, or shell history, and do not disable certificate verification.

The existing OWNER/REPOSITORY syntax also works for this private GitHub.com repository: use copilot plugin marketplace add octocorp/engineering-plugins as an alternative to the full URL above. Use a Copilot account with repository access, and authorize credentials for the organization's SAML SSO if required. The marketplace command reference documents a signed-in GitHub-token retry after HTTPS authentication fails, and /login if that retry fails. Enterprise membership alone does not grant access to every private repository. This example uses GitHub.com; a GitHub Enterprise Cloud deployment with data residency uses its own *.ghe.com hostname and requires host-specific setup.

Every user needs read access to the catalog repository and any separately referenced private plugin repositories. With "source": ".", the plugin is in the catalog checkout. If an entry points elsewhere, verify that source independently. A successful git ls-remote proves Git access to that URL; the marketplace and install commands still need to succeed.

If you only have one plugin, you can skip the catalog and install directly instead:

copilot plugin install https://github.com/octocorp/engineering-plugins.git

This assumes plugin.json is at the repository root. Direct installation does not create the engineering-toolkit@octocorp-engineering marketplace identity used in the catalog example.

After installation, start a new session, inspect the discovered components, and run a read-only task appropriate to your internal plugin. When troubleshooting, check network reachability, Git credentials, repository permissions, catalog name, and plugin name in that order. Recheck access when refreshing the catalog or updating the plugin.

Private hosting controls who can download the package. Installed files remain on the developer's machine, and loaded instructions can enter the selected model's context. Apply your organization's Copilot data-handling rules. A desktop's VPN, credentials, or SSH agent also do not automatically carry into a remote or cloud runtime; validate reachability and approved authentication there separately.

The private-source examples follow the documented Git URL formats. They have not been exercised against an authenticated private host in this walkthrough.

Installing in the Copilot app​

In the GitHub Copilot app, open Customize. Use the marketplace settings control beside the marketplace dropdown to add Azure/git-ape or its Git URL, then find the plugin in Browse and select Install. Use Installed to inspect the available source and version information and confirm the enabled state:

The screenshot shows the app's earlier layout; controls can move between releases. Check the current app customization guide, then try the same read-only prerequisite task.

Installing in VS Code​

Select the Copilot harness, then run Chat: Open Customizations. In the Agent Customizations editor, open Browse and choose Configure Marketplaces from the source menu. Select Add Marketplace and enter Azure/git-ape, then return to Browse and select that source. Review the plugin's publisher and included customizations before selecting Install. Accept any trust prompt only after reviewing the source.

If the unified Browse page is unavailable, use Plugins > Browse Marketplace. The Experimental chat.plugins.marketplaces setting is another way to configure the catalog. This installs an agent plugin; Git-Ape also offers a separately packaged VS Code extension, which is a different distribution route.

VS Code also discovers CLI-installed plugins under ~/.copilot/installed-plugins/. Its plugin guide notes that the /plugin interface and Agent Customizations editor have separate inventories, so manage the plugin through the interface where you installed it. Start a fresh session in the same harness and verify the prerequisite task.

Make adoption part of the repository​

Sharing commands works for early adopters. For a project team, put the intended plugin configuration under source control so it can be reviewed with the rest of the engineering environment.

For example, a consuming repository can include .github/copilot/settings.json:

{
  "extraKnownMarketplaces": {
    "git-ape": {
      "source": {
        "source": "github",
        "repo": "Azure/git-ape"
      }
    }
  },
  "enabledPlugins": {
    "git-ape@git-ape": true
  }
}

Copilot CLI documents enabledPlugins as declarative auto-install configuration. A plugin enabled only through this repository setting installs and activates for that repository, rather than becoming globally active in unrelated projects.

The keys do different jobs: extraKnownMarketplaces makes the catalog available, while enabledPlugins requests a specific plugin from that catalog. Registering a marketplace alone does not install every plugin it lists. Keep the marketplace key consistent with its catalog name, and use the complete plugin@marketplace identity.

The plugin-related keys are also read by Copilot in the cloud. A repository can declare the same plugin for CLI and cloud work without copying its skill files into each environment. Check component compatibility, dependencies, network access, and authentication on each surface.

In VS Code's Copilot harness, this file supplies repository plugin and marketplace defaults; users can turn off optional defaults in the Agent Customizations editor. In the Local harness, VS Code documents a recommendation notification and a browse/install flow. These are different behaviors. See workspace plugin recommendations and test your team's selected harness.

Repository defaults are optional. For the CLI, a developer can turn off the default in .github/copilot/settings.local.json:

{
  "enabledPlugins": {
    "git-ape@git-ape": false
  }
}

Add .github/copilot/settings.local.json to .gitignore; personal overrides should stay out of source control. Start a new session after changing the file. Enterprise-managed required or blocked entries take precedence over repository and local choices. GitHub's local override guide explains this distinction.

Review changes to .github/copilot/settings.json through pull requests, and protect it with CODEOWNERS and repository rulesets where appropriate. A repository template can seed the file for new projects, but existing repositories still need the change. These settings apply to the consuming repository. See the repository settings reference for supported keys and scope.

Update the catalog and the installed plugin​

After publishing changes, users can refresh the catalog and update the installed plugin:

copilot plugin marketplace update git-ape
copilot plugin update git-ape
copilot plugin list

The first command refreshes marketplace information. The second updates the plugin itself. Start a new session and check the loaded skills and agents before relying on the new behavior.

For plugins sourced from a local-directory marketplace, CLI loads the plugin live. Edits take effect in a new session or after /restart; plugin update has nothing to download. Do not treat this local development behavior as a test of remote upgrades.

In VS Code, open Plugins in the Agent Customizations editor and choose Check for and Apply Updates, or run Chat: Update Plugins. Automatic updates follow extensions.autoUpdate, except that npm and PyPI sources require a manual update and confirmation. Use the interface where you installed the plugin; see the VS Code update guide.

Choose an explicit update policy for custom marketplaces. The CLI update reference documents session-start auto-update through user or managed settings for interactive and -p sessions. This mechanism does not apply to SDK or server sessions, and a repository-level marketplace autoUpdate entry is currently ignored.

For a broad rollout, I would keep the release process simple:

  1. Review changes to instructions, scripts, hooks, dependencies, and external connections.
  2. Run the skill evaluations and compare results with the previous release.
  3. Publish a versioned release with notes explaining behavior and prerequisite changes.
  4. Test installation and upgrade with a pilot group before updating the wider audience.

Version strings help identify a release. To pin the downloaded code, the CLI supports marketplace sources using OWNER/REPO#ref. For example, replace ref with a reviewed full commit SHA. Check the installed plugin's resolved source as well: an external plugin referenced by the catalog needs its own revision control. A catalog's version field alone does not freeze a Git source.

Keep a way back​

If the plugin causes a problem, users can stop using an unmanaged installation without deleting their engineering project:

copilot plugin disable git-ape

Or uninstall it:

copilot plugin uninstall git-ape

For a local-directory marketplace, uninstall disables the plugin and leaves its source files on disk. This preserves the development checkout. Check copilot plugin list and the command output before assuming files were removed.

If repository defaults control activation, use the local override above or change the shared defaults through a pull request. Conflicting CLI enable/disable commands are rejected with the controlling settings path. Required managed plugins cannot be turned off locally.

A release rollback needs an earlier reviewed source revision and a check of the loaded version. Disabling a plugin stops its use; it does not restore an older release.

Keep a short record of the plugin version, source revision, client version, and observed failure. That gives maintainers something useful to reproduce, and connects the rollout back to the evaluations in article 2.

Now it's your turn​

Start by publishing a small marketplace and testing it with one other engineer. Then add repository configuration or managed rollout where that scope makes sense. Keep the installation simple, the update policy explicit, and the evaluation results attached to each release.
